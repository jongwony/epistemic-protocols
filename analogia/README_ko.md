# Analogia — /ground (ἀναλογία)

유비가 무엇을 허가하는지 감사 (ἀναλογία: 유비, 유추)

> [English](./README.md)

## Analogia란?

그리스어 ἀναλογία(유비, 유추)의 현대적 재해석으로, **추상 프레임워크가 지금 앞에 놓인 사례에 대해 무엇을 결론 내리게 허가하는지, 그리고 어디까지인지** 감사하는 프로토콜이다.

### 핵심 문제

AI는 한 도메인의 패턴, 모델, 유비를 다른 도메인에 적용하면서 구조적 대응이 성립하는지 확인하지 않는다. Strangler Fig 마이그레이션 패턴이 맞는 것 같지만 — 서비스가 단일 DB를 공유하는 모놀리스에서도 맞는가? 구조적으로 맞지 않는 추상적 조언은 구현 단계에서 낭비를 초래한다.

### 해결책

**보증은 인용된 증거를 따르지 동의를 따르지 않는다**: Analogia 는 이 유비가 무엇을 허가하도록 요구받는지 먼저 정하고, 두 도메인을 분해해 대응을 구성한 뒤, 각 대응에 대해 실제로 무엇이 그것을 받치는지 묻는다. 의도된 결론이 올라타는 주장마다 어떤 증거가 그 주장을 바꾸게 만드는지와 누가 그 증거에 닿을 수 있는지를 적고, 스스로 닿을 수 있는 검사는 직접 수행한 뒤, 각 결론을 한계와 함께 허가됨 · 차단됨 · 무엇이 빠졌는지와 함께 미결로 보고한다.

대응을 승인해 달라고 하지 않는다. 당신의 동의는 당신 코드베이스에 관한 증거가 아니고, 그 위에서 수렴하는 프로토콜은 구조가 아니라 당신의 확신을 기록하는 셈이 된다. 평가를 움직이는 것은 사실, 출처, 반례, 또는 무언가를 실행해 얻은 결과다.

### 다른 프로토콜과의 차이

| 프로토콜 | 주도자 | 타입 시그니처 |
|----------|--------|---------------|
| Prothesis | AI-guided | `FrameworkAbsent → FramedInquiry` |
| Aitesis | AI-guided | `ContextInsufficient → SufficientContext` |
| **Analogia** | **AI-guided** | **`MappingUncertain → MappingAssessment`** |
| Proplasma | Hybrid | `DirectionUnrecognizable → DirectionalContrast` |
| Merismos | User-initiated | `GoalPlanUncompiled → ConditionBearingUnitPlan` |
| Epharmoge | AI-guided | `ApplicationDecontextualized → ContextualizedExecution` |
| Katalepsis | User-initiated | `TargetUngrasped → VerifiedUnderstanding` |

**핵심 차이**:
- **vs. Prothesis**: Prothesis는 프레임워크가 없을 때 어떤 것을 적용할지 선택한다. Analogia는 선택된 프레임워크가 내 도메인에 구조적으로 대응되는지 검증한다.
- **vs. Aitesis**: Aitesis는 AI가 닿을 수 있는 사실을 모으고 사용자만 쥔 것을 이름 붙인다 (사실 관계). Analogia는 추상 구조가 내 맥락에 대응될 때 보존되는지 확인한다 (관계 구조).
- **vs. Epharmoge**: Epharmoge는 실행 후 적용성을 확인한다. Analogia는 실행 전 추상화 수준 간 대응 유효성을 확인한다.
- **vs. Proplasma**: Proplasma는 익숙한 도메인 매핑이 없고 방향의 미래가 서술로 인식되지 않을 때 폐기 전제의 placeholder probe로 대비한다. Analogia는 매핑이 존재할 때 그 구조 매핑을 검증한다 — 대비에서 생존한 방향에 매핑이 있으면 Analogia로 흘러 검증된다.

**판별 기준**: 불확실성이 *추상 구조 A가 구체 구조 B에 대응되는가*에 관한 것이면 Analogia다. *AI가 아직 닿을 수 있는 사실은 무엇이고 사용자만 쥔 것은 무엇인가*에 관한 것이면 Aitesis다. *어떤 프레임워크를 적용할지*에 관한 것이면 Prothesis다.

## 프로토콜 흐름

```
Phase 0: Detect       → 이 유비가 무엇을 허가하는지가 열려 있는가, 대상 설명은 이미 있는가 (비표시)
Phase 1: Assess       → 비교 초점과 걸린 결론을 정하고, 대응을 구성하고, 각 주장을 무엇이
                        무너뜨릴지 적고, 여기서 닿는 검사를 수행하고, 근거에서 보증을 읽고,
                        결론마다 판정한다
Phase 2: Surface      → 평가 전체를 제시하고 진행한다 (relay — 판정을 요구하지 않는다)
Phase 3: Integrate    → 근거를 인용하는 이후 발화가 평가를 다시 연다
```

이 프로토콜이 당신에게서 멈추는 자리는 비교 초점 하나다. 어떤 비교를 구성할지는 다른 무엇도 정해 주지 못하기 때문이다.

## 이후 발화가 하는 일

| 발화 | 효과 |
|------|------|
| **근거 인용** | 지목된 주장에 붙고, 보증을 다시 읽고, 모든 결론을 다시 판정한다 |
| **채택 / 철회** | 당신의 것으로 기록되고, 증거와 분리해 보고되며, 보증을 움직이지 않는다 |
| **그 밖의 것** | 답한다. 현재 기반 밖 증거가 필요할 때만 평가를 다시 연다 |

## 사용 시점

**사용**:
- AI가 패턴이나 아키텍처를 추천하지만 내 코드베이스에 맞는지 확신이 없을 때
- 추상적 조언이 이론적으론 맞는데 내 맥락에서 불명확할 때
- 도메인 간 유비가 구체적 검증 없이 적용될 때
- "내 상황에 이게 어떻게 적용되는지 보여줘"라고 할 때

**건너뛰기**:
- AI 출력이 이미 구체적 예시와 함께 도메인 특정적일 때
- 이 유비가 무엇을 허가하는지가 맥락에서 이미 정해졌을 때
- 추상 프레임워크가 적용되지 않을 때 (출력이 순수 구체적일 때)
- **두 도메인 중 하나를 처음 만나는 중일 때.** 그건 감사가 아니라 설명이다. 이 프로토콜은 당신이 이미 쥔 설명을 받아 그것이 무엇을 받치는지 묻는다. 설명 프로토콜을 먼저 쓰고, 설명을 손에 쥔 채 돌아오면 된다.
