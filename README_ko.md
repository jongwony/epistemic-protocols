# Epistemic Protocols

> [English](./README.md)

AI 협업이 방향을 잘못 잡으면, 전부 다시 합니다. 이 프로토콜은 방향을 정하는 결정을 일찍 드러내고 — 특히 계획 단계에서, 잘못된 방향이 코드나 다른 후속 작업으로 굳어지기 전에 — 각 결정은 직접 확정하도록 남겨 둡니다. 구현이 커지기 전에 방향부터 바로잡으세요.

## 왜 필요한가

모델이 좋아지면서 잘 쓴 프롬프트만으로도 많은 것이 됩니다. 중요한 것을 이미 다 적은 프롬프트라면 프로토콜을 쓰든 안 쓰든 결과가 거의 같을 수 있습니다.
어려운 것은 그 프롬프트를 쓰는 일입니다. 모르는 것을 한 번에 모두 떠올리고 실행 중에 만날 여러 경우까지 헤아려, 첫 답을 받기 전에 혼자 적어야 합니다.
프롬프트가 놓친 것은 나중에 드러나고, 늦게 드러날수록 비쌉니다. 계획 단계에서 잘못된 방향을 고치면 대화 한 턴이면 될 수 있지만, 이미 운영 중인 서비스에 배포된 뒤에 발견하면 그 위에 쌓인 모든 것만큼 재작업이 불어납니다.
프로토콜은 그런 결정 지점에서 AI를 사고 파트너로 만듭니다. AI가 물으면 그 질문이 떠올리게 한 것으로 답하고, AI가 후보를 제시하면 맞는 것을 알아봅니다. 작업을 결정짓는 항목 가운데 많은 것이 처음에는 적을 수 없었던 것들입니다.

예를 들어 "다음 주 회의 안내 메일 써 줘"라면:

| 결정 | 프로토콜 없음 | `/inquire` |
|---|---|---|
| 받는 사람 | AI가 혼자 정함 | 물어서 떠올려 답함 |
| 회의 목적(결정/공유) | AI가 혼자 정함 | 물어서 떠올려 답함 |
| 날짜·장소 | 물어서 답함 | 물어서 떠올려 답함 |
| 회신 요청 여부 | AI가 혼자 정함 | 제시되어 알아봄 |
| 분량 | AI가 혼자 정함 | 제시됐으나 고침 |
| 어조 | AI가 혼자 정함 | AI가 혼자 정함 |

실행 결과가 아니라 예시입니다. 어떤 항목이 어떻게 오는지는 모델과 사람에 따라 달라집니다. AI가 혼자 정한 결정이 그 때문에 틀린 것은 아닙니다. 다른 점은 그 결정이 나를 거쳤느냐입니다. `/inquire`는 이 항목들을 하나씩 묻지 않습니다. 먼저 스스로 닿을 수 있는 맥락을 모은 뒤 남은 것을 돌려주고, 물어보는 항목과 제시하는 항목은 그 한 번의 되돌림에 함께 옵니다.

여러 서브 에이전트가 일할 때 같은 차이가 어떻게 드러나는지 — 맡기기 전에 `/elicit` (누르면 영상):

<a href="media/elicit.ko.mp4"><img src="media/elicit.ko.gif" alt="같은 요청을 한 줄로 맡겨 서브 에이전트 셋이 빈칸을 제각각 채우는 경우와, /elicit으로 의도와 열린 결정을 먼저 확인한 뒤 맡기는 경우를 나란히 보여 주는 영상" width="720"></a>

<sub>영상 속 회사·이유·숫자는 각색한 예시이며 실행 결과가 아닙니다.</sub>

## 프로토콜이 도움이 되는 순간

계획 단계에서 잘못된 방향을 발견하고, 후속 작업으로 이어지기 전에 바로잡으세요. 같은 구조화된 점검 절차는 작업을 자율 실행에 넘길 때, 결과가 실제 상황에 맞는지 확인할 때, 이전 논의를 떠올릴 때, 무언가를 이해했는지 확인하고 그 위에 쌓아 올리기 전에도 도움이 됩니다.

## 빠른 시작

### Claude Code

모든 프로토콜을 [`route`](#route), [`epistemic-cooperative`](#epistemic-cooperative) 플러그인과 함께 설치합니다:

```bash
curl -fsSL https://raw.githubusercontent.com/jongwony/epistemic-protocols/main/scripts/install.sh | bash
```

`route`는 에이전트가 대화 맥락에 맞는 프로토콜을 호출하고 필요한 시점에 관련 협업 원칙을 찾도록 돕습니다. 그래서 어떤 프로토콜이 맞는지 몰라도 됩니다. 아직 실험 단계라 문구와 훅 구성이 릴리스마다 바뀔 수 있습니다. `epistemic-cooperative`는 가이드 학습(`/onboard`), 근거를 인용한 후보로 무엇이 막혀 있는지 알아보기(`/probe`), 컨트리뷰터 도구를 제공합니다. 둘 중 하나를 빼고 싶다면 설치 뒤 `claude plugin disable <name>@epistemic-protocols`를 실행하세요. `route`가 없어도 모든 프로토콜은 설치된 채로 각자의 명령으로 호출할 수 있습니다.

지금 서 있는 결정 지점에서 프로토콜을 직접 호출할 수도 있습니다 — 예를 들어 AI에게 작업을 넘기기 전에 `/inquire`, 작업에서 무엇을 결정해야 할지 아직 보이지 않을 때 `/bound`.

`/onboard`가 최근 세션 기반으로 빠른 추천을 주고, 원하면 시나리오·실행·퀴즈를 통한 가이드 학습으로 이어갑니다.

### Codex

이 레포지토리는 Codex 플러그인 marketplace이기도 합니다. GitHub에서 추가하려면:

```bash
curl -fsSL https://raw.githubusercontent.com/jongwony/epistemic-protocols/main/scripts/install-codex.sh | bash
```

로컬 checkout으로 개발 중이라면:

```bash
codex plugin marketplace add /path/to/epistemic-protocols
```

Codex marketplace는 Claude Code와 같은 플러그인 경계를 유지합니다: 각 프로토콜은 독립 플러그인이고, `epistemic-cooperative`가 유틸리티 스킬을 담습니다. marketplace는 [`.agents/plugins/marketplace.json`](./.agents/plugins/marketplace.json)에 있고, 각 플러그인은 Claude manifest 옆에 Codex manifest를 `<plugin>/.codex-plugin/plugin.json`으로 둡니다.

프로토콜의 체크포인트는 결정과 각 답이 바꾸는 것을 제시할 뿐 실행을 스스로 멈추지는 않습니다. 그래서 `codex exec` 같은 비대화형 실행에서는 결정이 작업이 시작된 뒤에 도착할 수 있습니다.

### 기타 에이전트 도구

프로토콜 스킬 원본은 각 플러그인 디렉터리의 `<plugin>/skills/<name>/SKILL.md`에 있습니다. 이 레포지토리는 더 이상 `.agents/skills/` 심링크 뷰를 미리 싣지 않습니다. Codex marketplace discovery가 플러그인 manifest와 Agent Skills 심링크를 함께 스캔하면 같은 스킬이 중복 노출될 수 있기 때문입니다.

[Agent Skills](https://agentskills.io/specification) 스타일 뷰가 필요한 호스트는 Codex marketplace checkout 바깥에서 별도로 materialize하거나, 호스트별 패키징을 사용하세요. 런타임 *tool grounding*은 여전히 도구마다 다를 수 있어, Claude Code 외 호스트에서의 프로토콜 동작은 cross-host 사용 증거가 누적될 때까지 잠정적인 것으로 다루세요.

### [Route](./route)

> **실험 단계.** 훅 구성과 주입되는 문구는 릴리스마다 바뀔 수 있고, 선택형 권고 채널은 아직 검증되지 않았습니다 — 어느 쪽이든 기대기 전에 [route/README_ko.md](./route/README_ko.md)를 확인하세요.

컨텍스트 기반 프로토콜 라우팅. 세션 시작 훅이 설치된 프로토콜의 결핍 테이블과 [premise](./premise) 색인을 컨텍스트 머리에, 컨텍스트 에포크마다 한 번 놓고, 매 프롬프트 훅이 프롬프트 옆에 짧은 지시문을 놓습니다. 이것이 있으면 어떤 프로토콜이 있는지 기억해 내지 않고도, 대화가 보이는 결핍을 그것을 해소하는 코어 프로토콜로 만나고 왜 그것이 왔는지 알아봅니다: 에이전트가 읽은 바를 보이고 분명한 적합이 가리키는 프로토콜을 진행 중인 작업과 합성해 호출하거나, 그렇지 않으면 적합마다 한 줄씩 가리키거나, 침묵합니다. 그동안에도 당신의 판단을 붙잡고 있는 다른 프로토콜의 게이트는 당신의 것으로 남습니다.

## 검증이 확인하는 것

검증 장치마다 확인하는 것이 다르고, 각자 어디서 멈추는지 알아 두면 도움이 됩니다.

- **Lean 증명** — 프로토콜의 계약은 `SKILL.md` 안에 Lean 모델로도 적혀 있습니다. Lean은 그 모델에 대해 적힌 성질이 모델이 선언한 가정 아래에서 성립하는지 확인합니다. 모델이 열어 둔 판단은 그 가정에 속하며, 증명되는 대상이 아닙니다. 프로토콜의 [`lean/EpistemicProtocols/<Protocol>/Theorems.lean`](./lean/EpistemicProtocols)에 그 모델에 대해 적고 증명한 성질이 있습니다.
- **런타임 증거** — 컨트리뷰터 스킬 [`/realize`](./.claude/skills/realize/SKILL.md)는 프로토콜을 실제 세션에서 실행해, 선언된 단계가 실제로 일어나는지에 대한 증거를 자동 검사와 대화 기록 검토로 모읍니다.
- **정적 검사** — [`/verify`](./.claude/skills/verify/SKILL.md)는 파일의 구조를 확인합니다: 필요한 섹션, 이름과 참조의 일관성, 버전 일치.

이 가운데 어느 것도 프로토콜을 쓴 뒤에 일어나는 일, 예를 들어 재작업이 줄었는지는 재지 않으며, 일부러 그렇게 둡니다. 프로토콜이 얼마나 도움이 되는지는 사람마다 아직 모르는 것이 무엇인지와, 계속 좋아지는 모델에 따라 달라지기 때문입니다. 실행 한 번이 보여 줄 수 있는 것은 처음부터 적혀 있어서가 아니라 AI가 묻거나 제시해서 대화에 들어온 결정이 무엇인지입니다. 컨트리뷰터 스킬 [`/outcome`](./.claude/skills/outcome/SKILL.md)은 같은 요청을 프로토콜 없이, 그리고 있이 실행해 그 결정들을 나온 구절과 함께 나열합니다.
