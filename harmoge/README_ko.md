# Harmoge — /fit (ἁρμογή)

구체적인 사례로 방향·설계·구현을 의도에 맞춰 가며, 보인 해 공간이 목적에 이만하면 충분해질 때까지 (ἁρμογή: 맞춰 이음 — 부분들을 하나로 맞물리게 함)

> [English](./README.md)

## Harmoge란?

그리스어 ἁρμογή(맞춰 이음, 접합)의 현대적 재해석 — **무엇을 원하는지는 알고 있고, 대상이 이미 눈앞에 있거나 곧 만들어지는데, 그것이 어디서부터 의도와 어긋나는지는 어떤 설명으로도 드러나지 않는 순간**을 위한 프로토콜입니다. AI가 인터뷰합니다. 지금의 해 공간을 보이고, 구체적인 사례를 판정해 달라고 묻고, 답을 대상에 반영하고, 호출한 뒤 쌓인 사례 전부를 다시 돌립니다. 보인 공간을 사용자가 목적에 이만하면 충분하다고 받을 때 닫힙니다.

### 핵심 문제

해 공간은 설명만으로는 의도와 융합되지 않을 때가 있습니다(`SolutionSpaceUnfused`). 규칙은 멀쩡히 읽히다가, 결코 받아들이지 않을 방식으로 처리되는 메시지 하나가 도착해서야 틀어집니다. 한 조항의 두 읽기는 둘 다 그럴듯하다가, 구체적인 사건 하나가 그 사이에 놓여야 갈립니다. 경계는 처음부터 있었고, 사례만이 그것을 보였습니다. 관측 가능한 증상: 몇 시간째 답이 없던 추상 질문이 예시가 오자 한 턴에 답이 남; 내용이 아니라 근거 때문에 거절하게 되는 권고; 마지막 답은 만족시키면서 앞선 답을 조용히 깨는 변경.

### 해법

**설명이 아닌 사례(Cases over Descriptions)**: 사용자는 Northstar와 목적을 쥐고 사례를 판정하고, 인터뷰는 AI가 합니다. AI는 자기 쪽에서 읽은 것 — 공간, 증거, 각 답이 이어지는 결과 — 을 사례로 가져옵니다. 매 라운드는 다음을 보입니다.

- **지금의 해 공간** — 지금 가장 맞는 것, 그것과 갈리는 대안, 그 대안들이 기대는 전제, 정의역, 사용자가 받아들인 타협, 아직 열린 경계.
- **지난 답에서 AI가 읽은 것** — 읽기마다 그것을 받치는 턴: 사용자의 턴, 도구가 돌려준 것, 또는 AI의 추론이라는 표시.
- **대상에 반영한 것**, 그리고 호출 뒤 쌓인 모든 사례에서 대상이 지금 하는 일 — 전체 요약과, 결과가 달라진 사례는 그 사례 그대로.
- **다음 질문** — 사용자만 쥔 것만, 본문을 보인 구체적인 사례로, 가장 크게 바꾸는 것부터. 사용자의 두 답이 다른 결과로 이어지는 사례도 물을 수 있는 사례에 듭니다. 다른 설계는 사용자가 아는 상황에서 실제로 했을 말로 보이고, 다른 것과 가르는 것 하나와 그 이유를 붙이며, 하나씩 차례로 보입니다.

사용자는 자기 말로 답합니다. 답은 그 말이 닿는 데까지만 묶습니다 — 필수, 허용, 금지, "전제가 틀렸다", "모르겠다"가 모두 답입니다 — 그리고 사용자가 든 이유나 예는 새 사례를 열거나 공간 전체를 옮길 수 있습니다. 사례에 대한 판정은 사용자가 바꿀 때만 바뀝니다. 판정한 사례에서 대상이 다르게 움직이면, 판정은 그대로 둔 채 그 사례로 보입니다.

보인 공간을 사용자가 의도와 목표에 이만하면 충분하다고 받으면 닫힙니다. 받는 뜻이 분명하면 AI는 어떻게 받았는지 말하고 나아가며, 잘못 읽었으면 사용자가 끊고 바로잡습니다. 증거에 비추어 그 결정이 사용자가 밝힌 목표와 부딪쳐 보이면, AI는 그 결과를 다음 사례로 가져올 수 있습니다. 기록은 그 공간입니다: 정한 사례, 받아들인 타협, 아직 열린 경계, 전제와 정의역, 공간의 실현인 대상, 사례마다 대상이 한 일. 대상이 사례에서 한 일은 실제로 돌려서 돌아온 것이 있을 때만 관찰된 것으로 칩니다. 아무것도 돌지 않은 곳 — 글로 된 설계, 방향 — 에서는 AI가 대상을 그 사례에 대어 읽은 결과이고, 읽기라고 표시합니다.

### 다른 프로토콜과의 차이

| Protocol | Initiator | Type Signature |
|----------|-----------|---------------|
| Katalepsis | User-initiated | `TargetUngrasped → VerifiedUnderstanding` |
| Euporia | Hybrid | `AbstractAporia → ResolvedEndpoint` |
| Periagoge | AI-guided | `AbstractionInProcess → CrystallizedAbstraction` |
| Hypotyposis | Hybrid | `FitUnrecognized → RecognizedForm` |
| Proplasma | Hybrid | `DirectionUnrecognizable → DirectionalContrast` |
| Analogia | AI-guided | `MappingUncertain → MappingAssessment` |
| **Harmoge** | **User-initiated** | **`SolutionSpaceUnfused → FusedSolutionSpace`** |

**이웃과 갈리는 기준**은 무엇을 무엇에 맞추느냐입니다. `/grasp`은 뼈대가 같고 맞추는 방향이 반대입니다: 그대로 있는 대상에 사용자의 이해를 맞추고, `/fit`은 사용자의 의도에 대상을 맞춥니다. `/elicit`은 의도 자체를 정합니다(무엇을 원하는지가 아직 분명하지 않을 때). `/induce`는 여러 사례가 공유하는 것에 이름을 붙입니다. `/sketch`는 만나서 알아본 한 버전에서, `/preview`는 받은 방향에서 끝납니다. `/ground`는 비교의 증거가 무엇을 지지하는지를 정합니다. **쥐고 있는 의도에 맞출 대상이 있고, 그 경계는 사례만이 보일 수 있음 → `/fit`.** 쓰다가 `/sketch`나 `/preview`와 겹치는 곳은 쓰임이 정하도록 둡니다.

## 파탄 조건 3종

| 파탄 | 가드 |
|------|------|
| 사례 대신 추상 읽기나 권고를 물음 | 다음 질문은 본문을 보인 구체적인 사례이고, 다른 설계는 사용자가 아는 상황에서 했을 말로 보인다 |
| 사용자의 답에 대한 AI의 읽기나 달라진 결과를 사용자의 판정으로 취급 | 판정은 사용자의 턴 위에서만 서고 사용자의 뒤 턴으로만 바뀐다; 읽기마다 받치는 턴을 댄다 |
| 대상을 읽은 것을 대상이 한 일로 보고 | 대상이 사례에서 한 일은 인용된 반환이 있을 때만 관찰이다; 아니면 AI의 읽기이고, 읽기라고 말하며 돌리려면 무엇이 필요한지 댄다 |

## 근거 문헌

설계가 기대는 문헌과, 이 프로토콜의 조사에서 각 출처를 확인한 강도(*verified*: 원문 확인; *mostly*: 핵심 주장 확인, 주변 세부는 종합):

- Mayer, M. 등 (2015). User Interaction Models for Disambiguation in Programming by Example (*UIST*) — *verified*. 후보 프로그램들이 서로 다른 결과를 내는 입력을 사용자의 실제 데이터에서 골라 묻습니다. 다음 사례는 답이 대상을 움직이는 사례라는 점을 정합니다.
- TiCoder — *LLM-Based Test-Driven Interactive Code Generation: User Study and Empirical Evaluation* (arXiv 2404.10100, 2024) — *verified*. 후보 코드를 실행해 물을 테스트를 고릅니다. 최고 순위 사례가 참조 구현의 전제를 어겨 아무것도 줄이지 못할 수 있고(§VIII-D), 잘못된 판정 하나가 유효한 후보 전부를 걸러 낼 수 있습니다(§VI-A). 사례는 사용자가 실제로 만날 사건이어야 하고, 답은 그 말이 닿는 데까지만 묶는다는 점을 정합니다.
- Smith, E. 등 (2015). Is the cure worse than the disease? Overfitting in automated program repair (*FSE*) — *verified*. 수리에 쓴 테스트를 통과한 패치가 따로 둔 테스트에서 실패합니다. 답은 그 사례만을 위한 예외가 아니라 대상이 해야 할 일로 반영하고, 다시 돌리기는 쌓인 사례를 덮을 뿐 새 사례는 따로 주장한다는 점을 정합니다.
- Mitchell, T. (1997). *Machine Learning*. McGraw-Hill, 2장, 버전 공간 — *mostly*. 원문에서 확인한 것은 버전 공간이 주어진 사례 모두와 일치하는 가설의 집합이라는 정의입니다. 후보 집합과 앞선 판정을 고정하면 새 판정이 집합을 넓히지 않는다는 것은 원문에서 읽은 것이 아니라 그 정의에서 따라 나옵니다. **가장 약한 연결**: "후보가 줄어든다"에서 "사람의 설계가 닫힌다"로 넘어가는 단계 — 실제 설계에서는 판단 기준 자체가 움직일 수 있으므로, 여기서 진전은 열린 질문 수가 줄어드는 것이 아니라 판정이 보존되는 것으로 읽습니다.

같은 과업에서 이 인터뷰와 단순한 경계 사례 요청을 직접 비교한 연구는 찾지 못했습니다(검색 범위: 예제 기반 프로그래밍, 반례 기반 요구사항 도출, LLM 요구사항 면담). 이 프로토콜이 단순 요청보다 무엇을 더하는지는 열린 경험적 질문입니다.

```
claude plugin marketplace add https://github.com/jongwony/epistemic-protocols

```

## 사용법

```
/fit [대상 — 방향, 설계, 또는 구현 — 과 그것이 무엇을 위한 것인지]
```

Harmoge는 대상에 닿는 것을 읽고, 지금의 해 공간을 보이고, 첫 사례를 묻습니다. 매 라운드 사용자는 자기 말로 답합니다 — 사례를 판정하고, 공간이나 목적을 고치고, 자기 사례를 가져옵니다 — 그러면 다음 라운드는 그 답이 대상에서 무엇을 바꿨는지와, 지금까지의 모든 사례에서 대상이 지금 하는 일을 보입니다. 보인 공간을 목적에 이만하면 충분하다고 받으면 닫힙니다. 언제든 그만둘 수 있고, 그만두는 것은 아무것도 받지 않으며, 그때까지 정한 것은 대화에 남습니다.
