# Boundaries and Safety

This document covers general safety discipline around actions that are hard to reverse: reading command-shaped text without executing it, mediating a dangerous effect rather than one spelling of it, establishing an artifact's actual provenance before trusting it, preserving a rollback path through a change, and making durable exactly the state that needs to survive an interruption.

## Command-Shaped Text Is Data Until Deliberately Run

Configuration text that is shaped like a command — anything using command-substitution syntax or similar evaluable constructs — crosses the boundary from data into code the moment it is evaluated. Evaluating it means running the enclosed command with whatever ambient authority the evaluating process holds, and that command can reach anything within that authority's scope. This is not a hypothetical: POSIX command-substitution semantics specify that the shell runs the enclosed command in a subshell and replaces the expression with the command's own output — the substitution syntax exists precisely to invoke execution, not to sit inert.

During inspection — reading a file to understand or analyze it — this evaluation step has no legitimate reason to fire. Read command-shaped configuration text as literal data: display it, quote it, reason about it, but do not pass it to anything that evaluates it. This is the operational form of a separation security engineering has long named: command injection (catalogued as CWE-78) is exactly the failure of maintaining that separation, and the primary defense named for it (in OWASP's guidance) is avoiding unnecessary invocation of operating-system commands in the first place, rather than trying to sanitize every dangerous string after the fact.

Scope this precisely, because it is an inspection-time rule and not a blanket ban on evaluation. Some configuration formats are deliberately executable — a build script, a shell profile, a hook definition meant to run — and evaluating such a format during its own normal runtime operation is exactly what it exists for; this principle does not forbid that. What it forbids is executing command-shaped text as a side effect of inspecting, browsing, or analyzing it, in a context that has no operational reason to invoke anything at all.

## Effect-Oriented Mediation

A safeguard that blocks one named command, one flag, or one code path defends against a spelling, not against the effect that spelling produces. A destructive replacement of an object — a file overwritten, a history rewritten, a record discarded — can usually be reached by more than one command, so a rule that watches for a specific banned string is bypassed by any other route to the same effect.

The corrective is to govern the effect rather than the name: identify the security-relevant outcome (an object is replaced, discarded, or made unrecoverable) and mediate every path capable of producing it, instead of enumerating individual commands one at a time. This is the discipline complete mediation names in reference-monitor design: a reference-validation mechanism must be invoked on every access to the resource it protects, not merely on the accesses that happen to route through one inspected choke point — a requirement general access-control guidance states directly (NIST SP 800-53). A mechanism that mediates by name rather than by effect is, by construction, incomplete mediation: it has a choke point for some paths to the effect and none for the others.

## Provenance and Identity Before Replacement

A file or object whose name suggests it is a backup, a snapshot, or a known-good copy is only a hypothesis about its own history — the name is a claim, not evidence. Before trusting such an artifact as the source for a restore or an overwrite, establish its provenance and integrity from evidence that does not depend on the name itself.

Distinguish what counts as independent evidence from what does not. A cryptographic hash or a digital signature identifies the actual content of the artifact — evidence about the bytes themselves, which is the standard basis digital-evidence provenance and data-integrity guidance describes for establishing what a recovered artifact actually is (NIST IR 8387; NIST SP 1800-11). A version-control reference — a commit hash, a tag — identifies a specific recorded state in a history: a different but similarly strong form of identity evidence. A size or an element count, by contrast, is weak evidence: many different artifacts can share a size or a count, so a match rules out little and a mismatch is merely suggestive.

Keep authorization and identity as separate questions. An explicit instruction from the person responsible for the artifact establishes that the operation is authorized — it does not, by itself, establish what the artifact actually is. Authority to act and identity of the thing acted on answer different questions, and treating one as evidence for the other is a category error even when the same person happens to supply both.

## Rollback Preservation and Baseline Validation

Before an operation overwrites existing state, preserve the pre-change state, and keep that preserved copy until the resulting state has actually been validated against an identified baseline. This is the same shape as rollback (undo) journaling in transaction processing: the pre-change state is recorded before the pages holding it are overwritten, and that record is retained through the entire commit sequence so recovery stays possible at any point before commit completes. Recovery guidance makes the same point operationally (NIST SP 800-34): a recovery is not complete when data has been restored, but when the restored state has been checked against a known-good baseline.

State the diagnostic posture honestly. When a restored or newly written state looks surprising, that surprise is a signal to stop and check — but check both ends: the identity of the baseline being compared against, and the state of the target that was changed. There is no established basis for treating the baseline as the more likely source of the discrepancy by default; that ordering is not supported by the sources this principle rests on, and asserting it would invite checking the wrong end first.

## Durability Before an Interruption Boundary

State that exists only in volatile memory — an editor buffer, an unsaved computation, a running process's working state — can be lost the moment the process holding it stops, whether by crash, by interruption, or by ordinary shutdown. Durable state, once written to a persistence layer that survives that boundary, provides a recovery point that volatile state cannot. Before crossing a credible interruption or failure boundary, make the state that actually matters durable.

This is the same requirement write-ahead logging imposes for crash recovery: the log record describing a change must reach permanent storage before the corresponding data is allowed to change, precisely so a crash between the two still leaves something durable to recover from. Ordering the durability write ahead of the risk is the substance of the guarantee, not an incidental detail.

Writing, saving, and recording a version are three different acts, and none of them stands in for the others. Writing a file can leave the result outside any tracked history, recoverable only if the file itself survives. Saving does not necessarily force the write down to durable storage — some save operations buffer, and their result can still be lost to a crash before that buffer is flushed. A version-control commit is a recoverable, addressable point in a project's own history, but it is a project-level record, not an operating-system-level durability barrier — it says nothing about whether the underlying write reached stable storage. Before choosing which act to perform, decide which property is actually wanted: bytes on stable storage, or a recoverable point in a project's history. They are not interchangeable, and performing the act that provides one does not automatically provide the other.
