# Route — /route

쌓인 세션 컨텍스트가 드러내는 결핍에 맞는 코어 epistemic 프로토콜로 라우팅하고, 그 프로토콜을 호출합니다.

> [English](./README.md)

## Route란?

각 epistemic 프로토콜 자신의 description은 그 프로토콜이 해소하는 상호작용 결핍을 명명합니다. 그것과 실제 호출 사이에 두 가지가 놓여 있고, 그중 하나만이 계기입니다. 다른 하나는 목록입니다 — 호스트의 loaded-skills 리스팅은 각 스킬의 description을 함께 실을 수도 있고, 커맨드 식별자만 실을 수도 있습니다. 식별자만 실릴 때 루프 위의 에이전트는 어떤 프로토콜이 무슨 결핍을 해소하는지에 대한 진술을 하나도 들고 있지 않습니다. 그러면 *컨텍스트가 로드된 어떤 프로토콜이 해소하는 결핍을 보여주는가* 라는 형태의 판별은 프롬프트 시점에 컨텍스트에 없는 목록에 대조하라는 요구가 되고, 결코 발동하지 않습니다.

이 공백은 드문 예외가 아니고, 하필 Route가 필요한 자리에서 가장 심합니다. 호스트가 리스팅을 크기 예산 아래 배급할 때 남기는 description은 최근 사용으로 정당화되는 것들이고, 떨어져 나가는 것은 사용자가 부르지 않아 온 스킬의 것 — 바로 Route가 닿으려는 집합입니다. 배급은 그렇게 Route의 목적과 반대 방향으로 작동하고, 조용히 그리고 부분적으로 그렇게 하므로, 채워져 보이는 리스팅이 정작 들어맞는 프로토콜 자리에서만 비어 있을 수 있습니다.

Route가 둘 다를 나눠 공급합니다: **언제는 훅들이 정하고, 무엇은 스킬이 정합니다.** `SessionStart` 훅이 판별에 필요한 목록을 컨텍스트 머리에, 컨텍스트 에포크마다 한 번 놓습니다 — 설치된 프로토콜마다 한 줄: 커맨드, 그것이 해소하는 결핍, 그리고 그것이 내놓는 resolution — 컨텍스트가 얇은 source에서는 여는 문장 아래에. `UserPromptSubmit` 훅은 매 프롬프트 옆에 짧은 지시문을 놓습니다. 호스트의 리스팅이 무엇을 실어 왔든 상관없이 판별이 프롬프트 시점에 평가 가능해집니다. `/route` 스킬은 호출되고 나면 로드된 프로토콜 식별자를 후보 집합으로 삼고, 각 후보의 결핍을 그 프로토콜 자신의 description에서 해소합니다 — 리스팅이 이미 그것을 실어 왔다면 아무것도 더 읽지 않습니다 — 그리고 정확히 하나의 프로토콜 결핍이 컨텍스트가 보여주는 것일 때 그 프로토콜을 호출합니다. description을 해소할 수 없는 후보는 이름이 무엇을 뜻할지 추측해 매칭되는 대신 후보에서 빠집니다. 호출된 프로토콜 자신의 Phase 0 감지와 첫 게이트가 사용자 판단의 자리로 남고, Route는 자기 게이트를 추가하지 않습니다.

테이블이 하는 일은 발동이지 매칭이 아닙니다. 턴이 어떤 결핍으로 흘러들었다는 것을 알아채는 데는 각 morphism의 양 끝 — 결핍의 이름과 그것이 바뀌어 가는 resolution — 으로 충분하고, 결핍은 홀로 있을 때보다 그것이 해소되어 가는 상태에 대조될 때 더 선명하게 읽힙니다; 그 쌍이 줄여 쓴 전체 서술은 실제로 매칭이 일어나는 `/route` 안에서 해소됩니다. 이 분업이 테이블을 프로토콜당 한 줄로 붙잡아 두고, 그것을 세션 시작에 놓는 것이 매 프롬프트 비용을 지시문 하나로 붙잡아 둡니다.

| 결과 | 조건 |
|------|------|
| 프로토콜 호출 | 로드된 프로토콜 하나가 지배적으로 맞을 때 |
| 프로토콜별 넛지 한 줄 (`↗ /command — reason`) | 여럿이 맞거나, 하나뿐인 매치가 약할 때 |
| 침묵 | 아무것도 맞지 않을 때 — 가장 흔한 경우 |

## 훅이 주입하는 것

`hooks/hooks.json`은 command 훅 세 개를 등록합니다. 셋 다 `hookSpecificOutput.additionalContext`를 쓰고, stdin의 payload를 읽되 필수로 요구하지 않으며, 모든 경로에서 0으로 종료합니다. 파일을 쓰지 않고, 네트워크를 건드리지 않으며, 세션 내용이 프로세스 밖으로 나가지 않습니다.

**`SessionStart` → `scripts/route-session.mjs`** 는 결핍 테이블을 컨텍스트 에포크마다 한 번 실어 나릅니다. 호스트는 에포크가 왜 시작됐는지를 payload의 `source` — `startup`, `resume`, `clear`, `compact` — 로 알려주고, 컴팩션 뒤에 이 훅을 다시 발화시키므로, 컴팩션이 테이블을 걷어낸 바로 그 시점에 테이블이 다시 컨텍스트에 들어옵니다 — 트랜스크립트를 읽지 않고, 마커도 두지 않고. 여기서 주입된 테이블은 컨텍스트 머리, 캐시된 프리픽스 안에 놓입니다. `startup`과 `/clear` 뒤에는 테이블 앞에 두 줄짜리 여는 문장이 옵니다: 컨텍스트가 얇고, 가장 먼저 확인할 결핍은 요청 자체에 있다 — 사용자만이 줄 수 있는 의도나 컨텍스트, 쌓인 컨텍스트가 아직 드러낼 수 없는 것. `resume`과 `compact`에서는 여는 문장 없이 테이블만 나갑니다: 잘려나간 뒤에 따라오는 결핍 — 세션이 이미 정리했으나 더는 시야에 없는 것 — 은 발화에 드러나고, 프롬프트마다 오는 지시문이 이미 그것을 라우팅합니다. 그래도 테이블은 다시 나가는데, 컴팩션이 앞선 주입을 걷어냈고, resume에서는 그것이 살아남았는지를 payload에서 읽을 수 없기 때문입니다. 두 훅은 불안정성이 어디에 있느냐로 갈립니다: 쌓인 컨텍스트가 이미 드러내는 결핍은 프롬프트마다 오는 지시문이 읽어내고, 사용자 쪽에 있어서 관찰이 아니라 물어야 드러나는 결핍이 세션 시작의 몫입니다. 여는 문장은 프롬프트마다 오는 지시문과 같은 동작으로 끝납니다: `/route`를 호출하라. 트리거는 둘, 라우터는 하나입니다 — 지시문의 조건(*쌓인 컨텍스트가 결핍을 드러낼 때*)은 요청 쪽에 있는 결핍을 구조상 놓치므로 여는 문장이 그 종류의 트리거가 되지만, 매칭 자체와 호출·넛지·침묵을 가르는 relay 판정은 `/route` 안에 있고, 여는 문장이 스스로 테이블에 대조해 버리면 그것을 건너뛰게 됩니다. 여는 문장은 조건을 말할 뿐 프로토콜 이름을 대지 않습니다 — 그것은 스킬의 Rule #2가 거부하는, 손으로 유지하는 라우팅 표가 됩니다. 그 아래 테이블의 머리글은 지시문 자신의 지시 대상인 *loaded core epistemic protocols*를 쓰므로, 두 주입이 하나의 목록으로 읽힙니다.

테이블은 유도되며, 유지되지 않습니다. `installed_plugins.json`이 활성화된 각 플러그인의 설치 경로를 주고, 스킬이 정확히 하나이며 그 `SKILL.md`의 MORPHISM 블록이 `deficit:`을 선언할 때 그 플러그인을 코어 프로토콜로 봅니다 — Route 자신은 제외되는데, 자기 자신으로는 라우팅하지 않기 때문입니다. 그래서 설치되지 않은 프로토콜은 나타날 수 없고, 스위트에 프로토콜이 추가돼도 여기를 고칠 일이 없으며, 손으로 동기화하는 목록이 없습니다. 선별 기준은 frontmatter의 `Type: (...)` 절이 아니라 `deficit:` 줄입니다. 그 절은 스위트 전체에서 균일하지 않아, 그것을 기준으로 잡으면 프로토콜 하나가 말없이 빠집니다; 그래도 `SKILL.md`가 그 절을 어디에든 싣고 있으면 행의 resolution은 거기서 오고, 없는 프로토콜은 결핍만으로 행을 유지합니다. 선별 규칙은 테스트에서 정식 프로토콜 레지스트리와 대조되므로, 규칙에서 벗어나는 프로토콜 — 스킬이 하나 더 붙거나 `deficit:` 줄의 모양이 바뀌면 — 은 테이블에서 사라지는 대신 테스트를 실패시킵니다. 모든 실패 경로는 열려 있습니다: 읽을 수 없는 payload는 `startup`으로 읽히고, 설정을 읽을 수 없거나, 설치 레이아웃을 알아볼 수 없거나, 해소된 프로토콜이 하나도 없으면 얇은 source에서는 여는 문장만, 잘린 source에서는 아무것도 나가지 않습니다.

**premise 색인이 같은 훅에 실립니다.** premise 문서들 — 프로토콜이 기대고 있는 협업의 전제들 — 은 이 marketplace의 플러그인들 옆 [`premise/`](../premise)에 함께 실려 오는 참조 표면입니다. 그 색인 — 각 문서와 그것을 부르는 순간 — 은 `scripts/route-premise.mjs`에, 항목이 이름 붙이는 순간의 종류로 갈라져(아래 `PreToolUse` 훅) 있습니다. 훅이 색인의 유일한 전달 채널이기 때문입니다: `premise/` 아래의 파일은 디렉터리 관례로 집혀 두 번 전달되는 두 번째 채널이 되고, 항목의 경로는 절대 경로일 때만 쓸모가 있는데 파일은 그것을 실을 수 없습니다. 옆의 테스트가 색인을 트리에 양방향으로 붙잡아 둡니다. 그 색인에 닿는 것은 그 자체로 하나의 셋업이었습니다: 한 호스트에서는 그것을 import 하는 전역 rules 파일, 다른 호스트에서는 instruction 파일의 포인터, 각각 호스트에 물어서 얻은 절대 경로를 들고 있어야 했습니다. 훅은 그 경로를 에포크마다 대신 해소합니다 — `known_marketplaces.json`이 이 플러그인이 설치된 checkout을 호스트가 어디에 두는지 기록하고, 그 아래 `premise/`가 이 레이어입니다; 어떤 기록도 checkout에 닿지 않으면 플러그인 루트 옆 `premise/`가 같은 디렉터리입니다 — 그리고 색인을 테이블 아래에, 모든 항목의 경로를 절대 경로로 바꿔 주입하므로, 항목이 이름하는 순간에 그 경로로 문서를 읽게 됩니다. Route를 설치하는 것이 셋업의 전부입니다. 색인은 테이블과 같은 이유로 모든 source에서 나갑니다: 컴팩션이 그것을 걷어냈기 때문입니다. 해소할 수 없는 색인은 빠지고 여는 문장과 테이블은 전과 같이 나갑니다 — 두 동반자는 서로 독립적으로 실패합니다.

**`UserPromptSubmit` → `scripts/route-prompt.mjs`** 는 `/route`의 발동 조건을 매 프롬프트 옆에 실어 나릅니다 — 네 줄짜리 지시문, 그리고 그것뿐입니다. 매 프롬프트 비용은 지시문 하나이고, 테이블은 에포크당 한 번 지불됩니다.

**`PreToolUse` → `scripts/route-edit.mjs`** 는 도구 호출이 어떤 표면을 바꾸려는 바로 그 시점에, 그 표면을 순간으로 삼는 premise 항목을 전달합니다. 색인은 항목이 이름 붙이는 순간의 종류로 갈립니다. 대화 속에서 오는 순간 — 결정하기, 제시하기, 완료를 선언하기 — 은 독자만이 알아볼 수 있으므로 그 항목은 세션 시작에 나가고 독자가 들고 다닙니다. 파일 조작인 순간은 호스트가 관찰할 수 있습니다: 도구 호출이 경로를 싣고 오고, 이 훅은 호출이 실행되기 전에 발화합니다. 그래서 순간이 지시 표면 — 프로젝트 지시 파일, 규칙, 원칙, 스킬, 에이전트 정의, 경로 모양으로 알아봅니다 — 의 변경인 항목은 여기서, 변경이 이루어지는 그 한 번에 나갑니다. 파일 도구는 경로를 그대로 이름 댑니다. 셸 명령은 표면 경로와 쓰기의 표지 — 리다이렉트, in-place 편집기, 복사나 이동, heredoc, write 호출 — 가 함께 있는지를 읽습니다. 표면을 읽기만 하는 명령은 그 순간이 아니기 때문입니다. 이 읽기는 휴리스틱이며, 읽기가 쓰기처럼 보인 경우에는 짧은 한 줄이 더 나가는 쪽으로 기울고, 보지 못한 쓰기는 프로젝트가 두는 지시 파일의 포인터가 여전히 닿습니다. Codex의 `apply_patch`는 패치를 `command`에 싣고 오며, 거기 이름이 나온 표면은 바뀌는 중입니다. 일치하는 것이 없으면 훅은 아무것도 쓰지 않습니다.

Codex는 같은 `hooks/hooks.json`을 읽고 세 훅을 모두 돌립니다. 유도가 Claude Code의 설치 기록을 읽으므로 Codex에서는 테이블이 비어 있고, premise 색인은 — 세션 시작에서든 편집 시점에서든 — 플러그인 루트 옆에 `premise/`가 있을 때만 나갑니다 — 그래서 Codex에서의 Route는 여는 문장, 지시문, 스킬 자신의 후보별 결핍 해소, 그리고 플러그인 루트가 이 저장소의 checkout 안에 있을 때의 색인으로 동작합니다.

## 설치

Claude Code:

```
claude plugin marketplace add https://github.com/jongwony/epistemic-protocols
claude plugin install route@epistemic-protocols
```

Codex:

```
codex plugin marketplace add https://github.com/jongwony/epistemic-protocols.git
codex plugin add route@epistemic-protocols
```

그 다음 플러그인의 훅을 검토하고 신뢰하세요 — 플러그인 설치가 훅을 신뢰하는 것은 아니며, Codex는 플러그인 동봉 훅을 현재 정의가 신뢰될 때까지 건너뛰므로, 이 단계 전까지 모든 훅이 꺼져 있습니다:

```
/hooks
```

Codex는 `hooks/hooks.json`에 적힌 훅 항목의 해시 — 이벤트와 명령줄이며, 그 명령이 실행하는 스크립트는 아닙니다 — 에 대해 신뢰를 기록하므로, 그 항목이 바뀔 때마다 이 단계가 반복됩니다.

Route를 설치하면 premise 레이어도 함께 전달됩니다: [`premise/`](../premise) 아래의 색인이 세션 시작에 주입되며, 손으로 연결할 것이 없습니다. 이전 셋업으로 연결해 둔 `rules/premise.md` import 나 instruction 파일의 포인터는 이제 같은 색인을 두 번 전달하므로 — 지우세요.

## 사용법

훅들이 일을 하므로 입력할 것은 없습니다. 현재 컨텍스트에 대해 같은 패스를 수동으로 돌리려면:

```
/route
```
